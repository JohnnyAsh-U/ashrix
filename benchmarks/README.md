# Ashrix benchmark suite

This suite compares the same HTTP workloads against (1) the application directly and (2) the Ashrix gateway. It preserves Vegeta raw results, JSON reports, text reports, and environment metadata.

## What it measures

- Small-request latency and request rate (`GET /health`)
- Download throughput and latency at 1 KiB, 16 KiB, 256 KiB, 1 MiB, and 10 MiB
- Upload + echo throughput and latency at the same payload sizes
- A small-request offered-load curve at 1, 10, 50, 100, 250, and 500 requests/sec
- Three repetitions by default, with a discarded warm-up for every case

This is an HTTP application-level benchmark. It does not directly measure QUIC handshake duration, UDP transport goodput, or isolated connector/gateway CPU usage. Capture those separately when running the suite on separate hosts.

## 1. Build and start the deterministic test application

From the repository root:

```bash
go build -o /tmp/ashrix-bench-app ./benchmarks/testapp
/tmp/ashrix-bench-app
```

By default, the app listens on `127.0.0.1:8081`; set `ASHRIX_BENCH_ADDR=0.0.0.0:8081` when it must be reachable on a private interface. It provides `/health`, `/payload?size=N`, and `/echo`. Payloads are generated once at startup; upload files are generated by the runner.

## 2. Install Vegeta

```bash
go install github.com/tsenart/vegeta@latest
```

Ensure `$(go env GOPATH)/bin` is on `PATH`.

## 3. Run the direct baseline

```bash
DIRECT_URL=http://127.0.0.1:8081 \
./benchmarks/scripts/run.sh direct
```

The direct baseline is loopback HTTP. It is useful for isolating Ashrix's added processing overhead in a same-host experiment, but it is not a realistic WAN baseline.

## 4. Start Ashrix and run the tunnel workload

Configure one gateway application with domain `grafana.example.test` and connector ID matching the running connector. Configure the connector application with the same application name and target `127.0.0.1:8081`. Start the gateway and connector using the normal documented CLI/configuration and ensure the gateway HTTP listener is reachable.

Then run:

```bash
ASHRIX_URL=http://grafana.example.test:80 \
./benchmarks/scripts/run.sh ashrix
```

Use the actual gateway listener address. If using HTTPS, use `https://...`; the benchmark client must trust the certificate chain and hostname. Do not disable TLS verification for published results.

## 5. Repeatability and resource measurements

Defaults are 20 seconds measured duration, 5 seconds warm-up, and 3 repetitions. Override them if needed:

```bash
DURATION=60s WARMUP=10s REPEATS=5 WORKERS=200 \
ASHRIX_URL=http://grafana.example.test:80 \
./benchmarks/scripts/run.sh ashrix
```

Run the gateway and connector under `pidstat` in separate terminals (or collect process IDs and use `pidstat -p PID 1`). Example:

```bash
pidstat -u -r -d 1
```

Also capture `ss -s`, `ss -u -a`, and file-descriptor counts during high-concurrency runs. Do not run both the direct and Ashrix tests simultaneously.

## 6. Compare results

Each run creates a timestamped directory under `benchmarks/results/`, including:

- `environment.txt`: host, kernel, Go, Vegeta and commit metadata
- `*.bin`: raw Vegeta results
- `*.json`: machine-readable Vegeta reports
- `*.txt`: text reports
- `summary.md`: consolidated report

Compare matching labels and repetitions between direct and Ashrix. Report median across repetitions where possible. Calculate latency overhead as `Ashrix latency - direct latency`; calculate throughput change as `(Ashrix throughput / direct throughput - 1) * 100`. Do not compare runs with different hosts, network conditions, payloads, offered rates, TLS settings, or software versions.

## Important limitations

- The direct baseline is localhost and the Ashrix path includes gateway + QUIC + connector + localhost app. This isolates the software path only when all components run on the same host. For realistic deployment performance, repeat with the load generator, gateway, and connector on separate machines.
- The Ashrix URL hostname must be the exact application domain configured on the gateway. For a same-host experiment, add `127.0.0.1 grafana.example.test` to `/etc/hosts`; for a remote gateway, use DNS or a hosts-file entry pointing that domain to the gateway address. This ensures the request URL hostname matches the gateway route.
- Vegeta's `-rate` is offered load, not guaranteed successful throughput. Check success ratio and achieved rate.
- The capacity sweep uses `/health`; it does not represent large-transfer capacity.
- A 10 MiB upload is echoed back, so the result includes both inbound and outbound transfer.
- No performance result is asserted by this repository. Results must come from actual runs on the target environment.

## 7. One-command sequential run

With the test app, gateway, and connector already running and correctly configured:

```bash
ASHRIX_URL=http://grafana.example.test:80 \
./benchmarks/scripts/run-all.sh
```

This runs the direct baseline first and the Ashrix path second. It does not start or configure gateway/connector processes because those require your real certificates and the normal Ashrix initialization/install flow.

## 8. Gateway and connector process monitoring

Find the process IDs, then run this in another terminal during a benchmark:

```bash
./benchmarks/scripts/monitor.sh benchmarks/results/resource-capture GATEWAY_PID CONNECTOR_PID 300
```

It records per-process CPU, RSS and I/O samples, plus socket and file-descriptor snapshots. Install `sysstat` if `pidstat` is unavailable. Use a separate monitor run for each benchmark phase if you need phase-specific measurements.
